NHK ONE：Cookie・認証ヘッダーの経路と自作プログラムでの試験
確認日：2026-10-10（日本時間）

後続結果：同日23:44、Chrome同梱CDMでも同じNHK認証に成功した。
CDMの差し替えと残る依存はcdm-replacement-report.txtを参照。
以下は23:05のTunePat同梱CDMを使った試験の記録。

結論

自作プログラムからNHKのライセンス認証に成功した。
対象は「北海道道 ファイターズ 日本一への道筋は」（Q4YVTYHXB2）。
23:05:45頃、明示承認された1回の送信に対しHTTP 200が返り、
同じCDMセッションで鍵3件が利用可能になった。CDM処理の終了コードは0。

TunePatの画面・制御コード・通信処理・独自中継ライブラリは起動していない。
ただし、ログイン状態はTunePatに保存された既存のものを読み取り、
CDMはインストール済みのTunePat同梱ファイルを使用した。
自前のCDMを作った結果でも、NHK動画のMP4保存まで確認した結果でもない。

1. 認証のつながり

NHKが公開する現在のページ・プレーヤーコードで、以下を確認した。

  NHKのログイン／視聴手続き
    → .web.nhk のCookieに視聴用トークン z_at を保持
    → ページの認証部品が accountAuthZ.accessToken 等として読み取る
    → プレーヤーの updateDRMToken → setDRMToken へ渡す
    → ライセンス要求に Authorization: Bearer <視聴用トークン> を付ける
    → https://licence.hsk.st.nhk/widevine/license へPOST
    → 応答をCDMへ渡す

ログイン用の n_at と視聴用の z_at は役割が異なる。
今回のライセンス要求に使ったのは z_at だけで、n_at は送信していない。
この経路はNHK自身の公開プレーヤー実装から確認した。
TunePatのメインプロセスが行う全ヘッダー加工を逆コンパイルした結果ではない。

TunePatの通常セッション用Cookie DBには、該当NHK Cookieがなかった。
内蔵ブラウザー用の Partitions/webviewsession/Cookies に z_at、n_at と
更新用Cookieが存在した。z_at はJavaScriptから読める設定で、
更新用Cookie bff-rt-authn / bff-rt-authz はHttpOnlyだった。
値の一覧やCookie DBのコピーは作成していない。

2. Cookieをそのままライセンスサーバーへ送る必要はあるか

今回の試験ではCookieヘッダーを送らず、視聴用トークンをBearerヘッダーに
付けるだけで、CDMが利用できるライセンスを取得できた。
ほかに送った明示的ヘッダーはContent-Type、Origin、Referer、User-Agent。
これらのどれが最小限必須かを切り分けるための追加送信はしていない。
特定の時点・アカウント・端末・番組での成功であり、全条件での保証ではない。

通常のCookie送信先として .web.nhk と licence.hsk.st.nhk は一致しない。
公開コードでは、ページがトークンを読み、別ホストへのライセンス通信に
Authorizationヘッダーとして明示的に渡す構造になっている。

3. 自作プログラムで行った最小試験

事前準備
・NHKの公開ページスクリプト33本と、参照先のプレーヤー本体1本を静的に確認。
・既存ログにある対象番組の配信一覧から、65 bytesの公開CDM初期化情報を取得。
・既存の z_at が有効期限内であることを、値を表示せずメモリ内で確認。
・外部送信なしで、CDMが1,717 bytesの要求を生成することを確認。

承認された本試験
・自作HTTP処理からNHK窓口へPOSTを1回送信。
・要求：1,717 bytes。応答：HTTP 200、1,063 bytes。
・CDMでの応答受け入れ、鍵3件の利用可能状態、正常終了を確認。
・セッションを閉じて終了。要求、応答、鍵の内容は保存していない。

この試験ではサービス証明書の取得要求ではなく、ライセンス要求を1回送信した。
同じ応答を別のCDMセッションへ再利用できることを示した結果ではない。
実際の動画復号・保存を続けるには、その処理まで同じセッション内で行う必要がある。

結果ファイル
  nhk-auth-trial/nhk-license-result.json
  nhk-auth-trial/nhk-license-attempt.json
  nhk-auth-trial/auth-evidence.json

4. ブラウザー内表示を使うアプリの構成

今回の成功により、次の構成は検証を進める根拠が得られた。

  アプリ専用ブラウザーでユーザーがNHKにログイン
    → 同じブラウザーセッションでNHKの視聴用トークン更新を扱う
    → 通信担当が有効なトークンを使ってCDMの要求をNHKへ送信
    → 同じCDMセッションで動画処理を行う

通常のiframeを置くだけで完了するという意味ではない。
自分のアプリが管理するブラウザー画面と、そのログイン状態の保持が必要になる。
試験ではTunePatの既存ログインを使ったため、アプリ専用ブラウザーでのログイン、
認証期限切れ、再ログイン、トークン更新はまだ実装・動作確認していない。

NHK公開コードには、同じサイトの /tix/token/refresh へCookieを伴うPOSTを送り、
更新後のトークンをプレーヤーへ渡す処理がある。今回のトークンは有効だったため、
更新要求は0回。自作プログラムでの更新可否を実証したとは扱わない。

5. 残っていること

・自作アプリ専用のブラウザーログインとトークン更新。
・同じNHKライセンスセッション内で、短い映像・音声の復号とMP4格納を確認。
・現在依存している同梱CDMの入手・配布方法を含むアプリ構成の確立。

Video Saver本体の保存機能は今回変更していない。
今回の成果は「NHKライセンス認証を自作プログラムで再現できた」ことであり、
NHK対応の完成済みダウンロードアプリではない。

6. データの取り扱いと送信回数

自作プログラムからのNHK認証付きライセンス送信：1回（ユーザーの明示承認後）。
Cookieヘッダー、パスワード、更新トークンの送信：なし。
視聴用トークンとCDM生成データの送信先：上記NHKライセンス窓口のみ。
動画セグメントの取得・復号：なし。
認証トークン、要求・応答本文、セッションID、鍵の内容のログ保存：なし。
アプリやCookie DBへの書き込み：なし。

初回の実行申請は自動承認審査で止まり、外部送信されなかった。
ユーザーの「1回送信して認証を試す」という回答後に1回実行した。
承認された1回は消化済み。スクリプトは送信試行記録がある場合に再送を止める。
