TunePat：制御処理から映像処理への受け渡し解析
確認日：2026-10-10（日本時間）
対象：TunePat VideoGo All-In-One 3.1.0 Appleシリコン版
対象ジョブ：NHK ONE、エピソード Q4YVTYHXB2、無料試用版の5分保存

追記：その後の静的解析で、ReadHeader / ReadPacketの呼び出し関係、引数の役割、
パケットから映像フレームへの受け渡し、付随情報とバッファの寿命を追加確認した。
更新結果はtunepat-frame-boundary-analysis.txtを参照。
以下は前段の調査記録であり、入力側の接続やデータ形式に関する未確定事項の一部は
次の報告で更新している。

結論

前回保存した1件のログを使い、制御処理から変換プロセスへの流れを確認できた。
制御側は共通のネイティブライブラリへ処理を渡し、その先でmedia_handleと
FFmpegの別プロセスが動く。FFmpegの入力には独自のmedia入力・media_decoderが
使われ、最終的に映像をH.264へ再圧縮している。

特に、次の二つの境界を特定できた。
  制御側 → libMediaConvert：QueryInterface / Execute / 各種コールバック
  FFmpeg入力側 → libTranscodeDLL：Initialize / ReadHeader / ReadPacket / Deinitialize

前者は静的な文字列・公開シンボルと、実行ログを組み合わせた根拠がある。
後者は同梱ライブラリの参照・公開シンボルと、ReadHeaderの実行ログが整合する。
ただし、コンパイルされた制御コードの全呼び出し順と引数の型・全項目は未復元。
この解析だけで、独自部品を置き換えた保存機能を再現できる段階ではない。

2. アプリ制御からネイティブ部品への入口

main/main_arm64.jscには、次の名前がまとまった手掛かりとして存在する。
  koffi / nativeLib / apiPointers / nativeCallback / ffiMap / ffiId
  getAllInterfaces / initializeCallback / uiOperationCallback / executeCallback
  QueryInterface / Execute / AbortExecute
  SetUIOperationCallback / SetUIOperationResult
  libMediaConvert.dylib / executeTool

libMediaConvert.dylibの公開シンボルとして実際に確認できた名前：
  Initialize、DeInitialize、QueryInterface、Execute、AbortExecute、
  SetUIOperationCallback、SetUIOperationResult

KoffiはNode.jsからCの関数を呼び出すためのFFIライブラリ。
一次資料：https://koffi.dev/
以上から、制御コードがKoffiを使ってネイティブの共通APIを呼ぶ構造が有力。
これはバイトコードの文字列とAPIの対応からの推定であり、Koffiの各呼び出しを
実行中に追跡したわけではない。

実行ログによる裏付け：
・アプリログ34行：20:00:07.195、MCライブラリの読み込み成功。
・アプリログ35行：20:00:07.225、getAllInterfaces。
・ネイティブ制御ログ23行：UI操作コールバックの登録。
・同37行：media_handleの起動。
・同40行：media_handle（PID 21990）がプロセス間通信へ接続。

「ネイティブ制御ログ」はcom.tunepat.vidicable.video.logを指す。
アプリログはTunePat VideoGo All-In-One.logを指す。
初期化はアプリ起動時に行われ、保存ごとに全体を起動し直す構成ではないと読める。

4. FFmpegと独自の入力部品の接続

media_handleはRUN/native/ffmpegを選び、次の設定を与えていた。
  入力形式：media
  入力デコーダー：media_decoder
  入力識別子：media://file
  出力映像エンコーダー：h264_videotoolbox
  品質指定：q:v 70
  時間制限：t 300（今回の試用版の300秒）

media://fileは、この処理の内部的な入力指定であり、NHKの動画URLではない。
この指定を通常のFFmpegへ渡すだけで同じ処理が再現できるとはいえない。

同梱のlibavformat.59.dylibには、libTranscodeDLL.dylibとlibTranscodeRecord.dylib、
Initialize / Deinitialize / ReadHeader / ReadPacketという参照がある。
libTranscodeDLL.dylib側には、対応する4関数が実際に公開されている。
libavcodec.59.dylibにはmedia_decoderとMedia Decoderの識別文字列がある。

この組み合わせは、独自の入力処理がライブラリを介してヘッダーとデータ片を
FFmpegへ供給する構造を強く示す。ReadHeaderは今回の変換ログにも出てくる。
ただし、各関数の引数、返す構造体、データ所有権や寿命、ライブラリ選択の分岐は
まだ確認していない。ReadPacketの各呼び出しも実行トレースで確認したわけではない。

5. 映像の再圧縮は確認できた

media_handle.logの59行には、次のストリーム対応が記録されている。
  rawvideo (media_decoder) → h264 (h264_videotoolbox)

30行のrecode 1、hwaccel 1、および出力MP4のエンコーダー情報とも一致する。
したがって、前回は「エンコーダー情報から再圧縮と整合する」としていた点を、
今回は「今回の保存では映像の再圧縮が実行された」と更新できる。

FFmpegへ渡された入力はyuv420p、1920×1080のrawvideoと記録されている。
後段の格納処理にはcopyも現れるが、その前にH.264への再圧縮が済んでいる。
このcopyは、最初から最後まで映像が無変換だったことを意味しない。

音声は少なくともこの変換段階でcopyとなっている。
音声経路全体で一度も変換されないとは断定しない。
字幕はmov_textへの変換指定があるが、完成ファイルで字幕が使えるかは未確認。

今回の経路は、配信断片の取得、復号関連の処理、rawvideoの入力、H.264への
再圧縮を含む。デスクトップの画面を実時間で5分収録する経路とは異なる構造が
ログから読み取れる。ただし、全サービス・全保存モードに一般化はできない。

6. 復号部品との境界で、分かったことと残ったこと

transcode.logにはCreateDecrypterとMappingServerの初期化が記録されている。
wv_shellのログにはCipher Data input end、Plain Data output endが記録されている。
静的にもlibTranscodeDLL、wv_shell、libdecryptにCipherData / PlainData / DecoderConfigや
MappingClient / MappingServerの識別文字列が存在する。

これらはプロセスを分けた暗号化データ・処理後データの受け渡しを示す根拠となる。
ただし、wv_shellのPlain Dataがそのまま映像フレームであるか、復号済みの圧縮データ
であるかは、このログだけでは確定しない。復号、デコード、フレーム包装の担当範囲と
呼び出し順を完全に解明したとは扱わない。

またnative2.log:90には、同じ処理区間に960×480のデコーダー初期化記録がある。
FFmpeg入力および出力の1920×1080という値との関係は未確認。
初期値、別の段階、解像度変更などの可能性を区別できておらず、元配信が1080pだった、
あるいは引き伸ばしたといった判断はどちらもできない。
再圧縮による画質差も、元の復号済み映像と比較できていないため定量化していない。

7. 今回の到達点

確認済み：
・共通のネイティブAPI名と、初期化・変換開始・終了の実行ログ。
・media_handle、FFmpeg、wv_shellが今回のジョブに関係すること。
・独自のFFmpeg入力・デコーダーの使用と、H.264への再圧縮。
・制御側の対象エピソードと変換完了の対応。

有力な構造上の推定：
・Koffiによる制御コードからlibMediaConvertへの呼び出し。
・libavformatの独自入力からlibTranscodeDLLの4関数への接続。

未復元：
・Executeなどへ渡す引数の完全な型・項目・検証規則。
・コールバックの完全な契約と、各モードの切替条件。
・復号部品からReadPacketまでに受け渡すデータの正確な形式と寿命。
・出力解像度と元の配信解像度の対応。

次に静的解析で絞るなら、libavformat側の独自入力がReadHeader / ReadPacketを
呼ぶ部分と、その戻り値をmedia_decoderが受け取る部分が具体的な境界になる。
今回特定したAPI名だけを使って、外部から安全・確実に呼べるとはまだ判断しない。
